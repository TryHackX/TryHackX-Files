# Przelewy24 integration

**Application version:** 2.76.10<br>
**Static protocol review:** 2026-07-29 against official Polish REST OpenAPI **1.0.17**  
**Provider documentation:** [REST documentation](https://developers.przelewy24.pl/) and
[OpenAPI source](https://developers.przelewy24.pl/yaml/pl_documentation_1.0.yaml)

This document describes the implementation in TryHackX Files. It does not replace the provider's
current documentation.

## Implementation status

Przelewy24 is a built-in checkout provider, not an HTML snippet or external bridge. The code
implements:

- merchant configuration stored through the encrypted payment-plugin settings;
- sandbox and production hosts;
- HTTP Basic authentication (`posId` plus REST API key);
- transaction registration and redirect to the returned token;
- signed transaction notifications and mandatory `transaction/verify`;
- status polling as a lost-callback recovery path;
- premium-plan and advertising purchases through the shared payment ledger;
- asynchronous refunds which remain `REFUNDING` until a valid signed result arrives;
- idempotent provider events, amount/currency/order correlation and monotonic fulfillment;
- separate permissions for premium payments/refunds and advertising review/refunds.

The protocol client is in
[`src/includes/repositories/P24.php`](../src/includes/repositories/P24.php), callbacks are in
[`src/includes/api/P24Controller.php`](../src/includes/api/P24Controller.php), and the shared
fulfillment fallback is in
[`src/includes/repositories/PaymentReconciler.php`](../src/includes/repositories/PaymentReconciler.php).

The implementation has deterministic, network-free tests. A real sandbox run remains blocked
until merchant credentials are available.

## Configuration

Open **Administration → Premium → Payment plugins → Przelewy24** and save:

| Field | Meaning |
|---|---|
| Merchant ID | P24 merchant identifier |
| POS ID | REST Basic Auth login; usually the POS/account identifier |
| CRC key | secret used only for SHA-384 signatures |
| API key | REST Basic Auth password, also called the reports/API key |
| Currency | default account currency |
| Environment | `sandbox` or `production` |

Saving a complete built-in provider selects it as the active built-in checkout for both Premium
and advertising purchases. Secrets are encrypted by the application's `APP_SECRET_KEY`.

The callback URLs are generated from the canonical application URL:

```text
https://files.example.com/api.php?action=p24_notify
https://files.example.com/api.php?action=p24_refund_notify
```

They must be publicly reachable over HTTPS in production. They intentionally do not use browser
CSRF tokens: authenticity comes from the P24 SHA-384 signature and is checked before state
changes.

## Protocol contract

Hosts:

- sandbox: `https://sandbox.przelewy24.pl`
- production: `https://secure.przelewy24.pl`

REST authorization uses HTTP Basic with `posId` as the login and the API key as the password.
The CRC key is never used as the REST password.

Signatures are SHA-384 hashes of JSON encoded with
`JSON_UNESCAPED_UNICODE | JSON_UNESCAPED_SLASHES`. Key order and integer amount types are part
of the protocol:

| Context | Ordered JSON fields |
|---|---|
| registration | `sessionId`, `merchantId`, `amount`, `currency`, `crc` |
| payment notification | `merchantId`, `posId`, `sessionId`, `amount`, `originAmount`, `currency`, `orderId`, `methodId`, `statement`, `crc` |
| verification | `sessionId`, `orderId`, `amount`, `currency`, `crc` |
| refund notification | `orderId`, `sessionId`, `refundsUuid`, `merchantId`, `amount`, `currency`, `status`, `crc` |

Amounts are integers in the smallest currency unit.

### Payment flow

1. TryHackX Files persists a `NEW` ledger row and immutable product snapshot.
2. `POST /api/v1/transaction/register` creates the provider transaction. TryHackX Files sends the
   documented `country` field (`PL` by default) and `timeLimit=0` (no provider-side expiry).
   The published OpenAPI 1.0.17 `required` list still says `ttl`, but its actual field
   definition, REST request sample and usage guide consistently use `timeLimit`; the client
   follows those current request examples.
3. The browser is redirected to `https://{host}/trnRequest/{token}`.
4. P24 posts a signed JSON result to `p24_notify`.
5. TryHackX Files validates the signature, merchant/POS, local session, provider order, exact amount
   and currency.
6. TryHackX Files calls `PUT /api/v1/transaction/verify`. A notification alone never grants a product.
7. The shared reconciler atomically fulfills the plan or advertising purchase. Duplicate
   callbacks are harmless.
8. If a callback is lost, cleanup reconciliation calls
   `GET /api/v1/transaction/by/sessionId/{sessionId}` and still performs mandatory verification
   before fulfillment.

P24 transaction status values used by the fallback are:

- `0`: no payment;
- `1`: advance/prepayment state;
- `2`: payment made;
- `3`: payment returned.

### Refund flow

1. An authorized moderator or administrator claims a durable refund lease.
2. TryHackX Files stores `requestId`, `refundsUuid`, refund token and actor in payment metadata.
3. `POST /api/v1/transaction/refund` submits the request and its `urlStatus`.
4. HTTP 201 only changes the local state to `REFUNDING`; it does not revoke access or mark the
   payment refunded.
5. The signed callback is correlated with UUID, request ID when present, order, session, exact
   amount and currency.
6. `status=0` atomically sets `REFUNDED` and revokes an entitlement only when it is still tied
   to that payment. `status=1` releases the lease for a controlled retry.

## Sandbox acceptance checklist

Complete this checklist before production:

- [ ] `GET /api/v1/testAccess` succeeds with the exact saved configuration.
- [ ] Registration returns a token and the P24 test checkout opens.
- [ ] A successful payment sends a valid callback and `transaction/verify` succeeds.
- [ ] The ledger moves `NEW → PENDING → COMPLETED` exactly once and grants the correct product.
- [ ] An identical payment callback is idempotent.
- [ ] Invalid signature, merchant/POS, order, amount and currency never grant a product.
- [ ] A lost callback is recovered by status polling plus mandatory verification.
- [ ] An accepted refund stays `REFUNDING` until the signed result.
- [ ] A valid successful refund moves to `REFUNDED` exactly once.
- [ ] Duplicate, tampered and rejected refund callbacks cannot revoke or finalize incorrectly.
- [ ] Premium and advertising purchases both expose the correct invoice after completion/refund.
- [ ] Discounted amount and immutable product snapshot remain consistent through fulfillment.

Do not test production payments with real money until the full sandbox checklist passes and the
current provider specification has been compared again.
